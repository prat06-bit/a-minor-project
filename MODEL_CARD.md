# Model card: synthetic PMIS matching prototype

## Intended use

Educational experimentation on candidate-opportunity matching, data quality, ranking, and capacity constraints for the MAIT minor project. This prototype is not approved for selecting, rejecting, or allocating real applicants.

## Data

The supplied workbook contributes internship opportunity/reference attributes and aggregate application counts. It contains 1,062 unique Main-sheet internship IDs plus state and district aggregate tabs. It does not contain candidate-level decisions or verified selection labels. Synthetic profiles, pairs, and targets are generated by `src/pmis_pipeline.py` using the configured seed and source distributions.

## Target

`synthetic_proxy_label` is 1 only when generated eligibility passes and a weighted synthetic suitability score plus seeded noise meets a configured threshold. It is a simulated heuristic target. Metrics measure agreement with this rule and do not establish actual PMIS selection accuracy, candidate utility, or causal benefit.

## Features and safeguards

Features represent qualification/course compatibility, token overlap, sector and location preferences, capacity, and generated past participation. Eligibility is separate from score. Sensitive attributes are not used as ordinary merit predictors. No official affirmative-action policy is embedded; optional policy constraints must remain separate from merit scoring and be backed by an authorized rule set.

The live dashboard uses a documented rule-based baseline; it does not load a fitted classifier. Its six compatibility weights are defined in `src/pmis_pipeline.py`. The source catalog retains the source internship IDs, while the capacity-allocation demonstration uses a separately generated 350-opportunity scenario. Candidate CSV uploads are session-only and are never merged into the generated dataset. An explicitly supplied group column can be used for descriptive allocation-rate reporting or one configured minimum-allocation constraint; it never changes the compatibility score.

## Evaluation

Candidate-grouped holdout comparisons include a transparent rule baseline, Logistic Regression, Random Forest, and Gradient Boosting. Classification, ROC-AUC, PR-AUC, NDCG, confusion counts, elapsed time, and allocation capacity checks are emitted. Results are specific to generated data and must be labeled accordingly. Current reports do not establish generalization to real companies or unseen official applicant populations.

The updated evaluation pipeline also emits NDCG@5 and NDCG@10. The checked-in metrics predate those cutoff metrics and must be regenerated to populate them. Allocation validations separately report capacity and eligibility violations.

## Known limits

- No real candidate-level source data, historical outcomes, skills text, or validated preference behavior.
- Source aggregate application counts may exceed listed capacity; those values are preserved and cannot be interpreted without the official field definitions.
- Skill similarity is token overlap, not a validated semantic embedding model.
- Synthetic labels encode the same assumptions used to evaluate the models.
- No demographic or authorized policy-group fields are generated by default. Optional group-rate diagnostics and group minimums require an explicitly supplied field and are not evidence of fairness, policy compliance, or improved outcomes.
- Current source-based profiles and location samples can reproduce catalog imbalance.

## Change control

Record changes to generator rules, label weights, data schema, source workbook, seeds, and corruption settings in manifests. Never merge generated records into an official source layer or rename proxy labels to real outcomes.
